## Answer to the framing question: pre-warm every route, or code better?

Code (and the database) — pre-warming cannot reach the problem:
- The slow pages are **per-entity and per-parameter**: 957K filing pages, 1.1M donor pages, 5,134 lobbying pages, 1,471 race pages × every scope preset, 129 states × 19,805 cities × scopes × page × sort on the geo drill-down, every search string. That key space cannot be prewarmed, and a crawler walks it.
- The existing prewarm is itself a cost: it runs **inside every gunicorn worker** (3 copies of the same builds on each restart, 2–3 minutes of CPU each), covers only the default current-cycle keys, and the Sunday refresh flushes Redis **without** re-warming, so the site cold-starts under traffic.
- What does scale: make each per-page query an index probe (A15/A16 pattern), remove the per-request taxes every page pays, bound the cost of any single request, cache the few heavy aggregate pages in Redis with long TTLs and single-flight, prewarm the *finite* preset windows once from the refresh chain (not per worker), and keep crawlers off the expensive query-string surface.

Sources: eight-reader sweep + local measurement + critique (`wf_d91f4314-ee0`; digest `scratchpad/load_time_digest.txt`; journal path in `profiles-races-dated-widgets.STATE.md`). Prod figures below marked (prod) were measured 02:17–02:45Z while load was 9–10 and the readers themselves were hitting the site, so they are upper bounds; local figures are from the M3 Pro with the prod data copy.
