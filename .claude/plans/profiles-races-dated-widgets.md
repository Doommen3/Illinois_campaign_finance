## 2. Design

### 2.1 Committee profile (Lane P)
- **Order** (Devin's pick, 2026-10-26; bar first, then): Receipts Summary | Expenditures Summary → Top Donors | Top Payees (two-column) → Committee Information → Linked Candidates → Current Officers → Filing History. The 527 org page (`irs527/detail.html`) gets the same treatment (Devin: yes, 2026-10-26): Financial Summary → Top Contributors | Top Expenditure Recipients → the rest → Filing History last.
- **One feeder, two consumers.** New helpers in `webapp/routes/committees.py` (`committee_donor_rollup`, `committee_payee_rollup`, each with a `_count` twin) take `(conn, committee_id_sbe, scope, *, limit, offset, sort_by, sort_dir)`; the profile's Top-20 and the new full-list pages both call them, so the top-N is always the head of the full list.
- **Donor identity = `donor_key`** (the site formula; J-P3). Each row: display name (as filed), city/state, total, count, first/last date, link to `/donors/key/<donor_key>?source=bulk` (+ `**scope_query`). **Payee identity = normalized name** (J-P4), unlinked.
- **Predicate = `_bulk_receipts_base_filter_sql()`** semantics (amount > 0, not archived, d2 part blank or Part 1) so the donor list reconciles with the donor profile's windowed total (J-P5). Payees: not archived, amount > 0.
- **Pages:** `/committees/<int:committee_id>/donors` and `/committees/<int:committee_id>/payees` (resolve the ISBE id exactly like the profile), 50/page, sort links (`total`, `count`, `name`, `last`), optional `q` name filter in a page form carrying hidden scope inputs, bar with the profile's default (`all` + "This cycle" subtotal), `<h2>Donors {{ scope_tag() }}</h2>` + "N unique donors, $X" summary line. Profile Top-20 tables get "See all N donors →" / "See all N payees →" links.
- **Index:** `idx_isbe_condensed_expenditures_committee_date (committee_id, expended_date)` added to the matview DDL (`scripts/isbe_sunshine_etl.py` ≈ L531) so every import carries it; created once on prod at deploy with `CREATE INDEX IF NOT EXISTS` (the ETL only rebuilds on the next import).

### 2.2 State races (Lane R)
- **Index page** `/analytics/state-races/` (template `analytics/state_races.html`): every race of the resolved cycle in one scrollable table, same columns and sort controls as the overview. **Activity = windowed receipts (`total_amount > 0`) or windowed Part-9 outside spending** (D-2 totals are not windowed, so they do not count — gate). Rows with activity link to the detail page; rows without render unlinked and greyed. Summary line: "443 of 599 races have activity in <window label>". No toggle, no client-side filter box (gate: not asked; the browser's find-in-page covers it).
- **Overview link:** "See all N state races →" under the Top-12 table, carrying `**scope_query` + `election_cycle` + sort. Detail page gets an "All state races" link beside "Back to Top State Races".
- **Shared build + cache:** `_get_state_race_rows(filters, election_cycle, sort, dir)` in `routes/analytics.py` caches the FULL row list under `("state_races", time_period_key, election_cycle, sort, dir)` with the overview TTL; `dashboard()` slices it `[:12]` instead of calling the builder itself, so the index is free once the overview (or prewarm) has run and the two pages can never disagree.
- **Cycle coherence:** when the scope is a cycle preset (`scope_cycles(scope)` → one cycle) and `?election_cycle=` is absent, the candidate set uses that cycle; otherwise today's MAX-cycle behaviour stays, labelled "Candidates: 2026 cycle" on the page.
- **Archived fix:** add `NOT COALESCE(r.is_archived::boolean, FALSE)` to the race builder's receipts scan when the column exists (same guard as the expenditures scan). Numbers on the overview, index and detail drop accordingly — expected and correct.

### 2.3 Dated-widget registry (Lane W)
- **Registry** `tests/scope_widgets_registry.py` (nothing at runtime reads it — gate): a tuple of `Widget(endpoint, url, template, heading, kind, status, axis, ordinal=1, covered_by=None, note="")` with `status ∈ {window, fixed, partial, mismatch}` taken from the inventory's column J. Located in rendered HTML by its `<h2>` **or `<h3>`** heading text plus `ordinal` for duplicates (e.g. `candidates.html` has two "Candidates" headings), sliced to the next heading of the same level.
- **Completeness test** `tests/test_scope_widgets.py::test_every_windowed_tag_site_is_registered`: parses every windowed `scope_tag(` call (no argument, or a fixed-cycle text) in `webapp/templates` with the heading on that line → each must be in the registry. One-way only (gate: a reverse "stale entry" check fires on copy edits; the harness GETs every registered URL anyway).
- **Doc** `docs/date_filtered_widgets.md` stays the hand-built, dated snapshot (it carries file:line refs, the window analysis and the coverage column, which a generated table would lose — gate); it points to the registry as the live list. No generator, no freshness test.
- **Behaviour harness** `tests/test_scope_widgets.py`: **one test per page** (gate: fixture authoring, not suite time, is the cost). Only `status=window` table/list/chart rows are probed (inventory column J = yes: 81 rows, 17 already covered by real in/out page tests → recorded as `covered_by`, ~64 net-new). Each page test GETs the route at an explicit `date_from/date_to` and asserts, inside each registered widget's slice, that an IN-window marker row appears and an OUT-window marker row does not; charts use month / node-label markers in their embedded JSON. Reuses the OUT rows the existing fixtures already carry (`profile_app` 2023 receipt, `donor_app` 2023 Alice, `lobbying_list_app` 2022 entity) and tops up fixtures only where a page has none — no new seeder module. `fixed` rows are not probed; `partial` / `mismatch` rows are recorded, not asserted, until their fix flips them to `window`. Fixes the OpenBook assertion that cannot fail (E7).
- **Stat cards** (J-W3, Devin: yes, 2026-10-26): the ~17 windowed stat-card rows with no page-level test get a "windowed total ≠ all-time total" check in the same page tests; partial cards are recorded only. Not literally "charts and tables", but aggregate cards are what visitors read first, and a `scope_where` regression that breaks only aggregates would pass every table-marker test.
- **Process rule** (CLAUDE.md Time-scope bullet + README): a new windowed widget must be registered or CI fails; the full suite (CI on every push) already runs `tests/test_scope_widgets.py`.

### 2.4 Candidate profile (Lane C — Devin, 2026-10-26: "a candidate profile that shows all of their committees with the most recently active toward the top, in a way that a user can tell which have been active most recently")
- **Route** `/candidates/<int:candidate_id>` (ISBE `isbe_candidates.id`) in a new module `webapp/routes/candidates.py` (blueprint `candidates`, prefix `/candidates`; the existing landing `/candidates` in `main.py` is untouched). Template `candidates/detail.html`. Scope bar like the other profiles: default `all`, axis `received`, "This cycle" subtotal, source ISBE.
- **Header**: name, office + district type/district, party, residence county; candidacies summary (years run, last outcome).
- **Committees table (the point of the page)**, one row per linked committee from `isbe_candidate_committees`, **sorted by last activity, newest first**: name (link to the committee profile), ISBE status (Active / Inactive), **Last activity** = date + what it was (receipt / expenditure / filing), last filing name, raised and spent in the window, first and last activity years. Rows active within the last 12 months of `data_through` get a "Recently active" badge; rows with no activity in 4+ years are visually muted. Last activity = `GREATEST(last non-archived receipt date, last non-archived expenditure date, last filing received date)` from `isbe_condensed_receipts`, `isbe_condensed_expenditures` (index from 0.1) and `isbe_most_recent_filings`.
- **Candidacies table**: election year, election type, race type (incumbent / open seat / challenger), outcome — from `isbe_candidacies`, newest first. `{{ scope_tag('All time') }}`.
- **Money by cycle**: receipts per election cycle across all the candidate's committees (`scope_cycles` granularity, tagged fixed) — the quick read of a career.
- **Links in**: committee profile "Linked Candidates" rows, search results candidates section, race detail candidate rows, candidate-finance list rows. Committee families (C8) are a later layer on this page: when approved, committees in the same family render grouped under one heading.
- **Tests** `tests/test_candidate_profile.py`: fixture candidate with three committees (one active with a 2026 receipt, one inactive with a 2022 expenditure, one inactive whose last trace is a 2019 filing) → row order and "last activity" labels asserted; badge rules; bar default all time + cycle subtotal; the four inbound links; 404 for an unknown id.

### 2.5 Committee consolidation (design only; see suggestions C8 — nothing lands without Devin's yes)
Two different phenomena, two different answers:
1. **Serial re-registration** (same actor, new ISBE id each time; 806 exact-name groups, 721 same-candidate near-names): group, do not merge. A `committee_family` (+ `committee_family_member`) table mirroring the donor merges, seeded by an evidence rule — same linked candidate AND (same normalized name OR trigram ≥ 0.8 OR same treasurer/officer OR same address) — and reviewed in an admin page modelled on `/admin/donor-merges`. Display: a "Part of the Friends of X family: 3 committees, 1 active" banner on committee pages, grouped rows on the candidate profile, and an opt-in "by family" rollup on lists and top-N widgets. Committee ids and their pages stay as they are; totals are never silently merged.
2. **Genuinely distinct look-alikes** (PAC vs IE PAC, same-named referendum committees in different districts): never merged; the evidence rule plus review keeps them apart. The 143 same-zip near-name pairs with no shared candidate are the review queue's first batch.
The candidate profile (Lane C) already consolidates the most common case for readers — every committee of one candidate on one page, newest activity first — without any data model change.
