## Findings (scout survey 2026-10-28, HEAD 9eb07a7)

**Ask 1 — why a header click only sorts 12 rows.**
- The overview builder `dashboard()` (`webapp/routes/analytics.py:632-740`) gets the full race list through `_get_state_race_rows` (`:543-563`, `limit=100000`; ~1,761 races in the largest cycle), which `get_state_race_analytics` (`database/analytics.py:3160`) sorts in Python (`:3181-3190`) by a whitelisted field; the overview keeps the first 12 (`:723-724`).
- The preview table (`webapp/templates/analytics/overview.html:96-140`) is a plain `table.data-table`, so `webapp/static/js/table_sort.js` (global, `base.html:167`) sorts the 12 DOM rows on header click. A separate GET select `state_race_sort` / `state_race_dir` (`overview.html:42-52`) re-requests the page with a server sort; the two mechanisms do not know about each other.
- Whitelist `_STATE_RACE_SORTS` (`webapp/routes/analytics.py:495`) = `total_amount`, `outside_spending_total`, `outside_pressure_ratio` only. The preview shows eight columns: Race, Candidates (cycle), Donors, Contributions, Total Amount, Outside Spending (E), Outside Pressure Ratio, Top Candidate Share (cycle).
- Cache cost today: `_overview_cache_key` (`:604-630`) and `_state_races_cache_key` (`:519-527`) both carry sort and dir, so the overview is fragmented 3×2 and every variant re-runs the whole race build (the builder takes no sort; `database/analytics.py:3170`). The warm script warms one variant.
- `/analytics/state-races/` (`:783-825`) renders all rows with no LIMIT (`state_races.html:27-50`, also client-sortable). No JSON endpoint serves the race list.

**Ask 2 — nothing per-entity exists.**
- The eight views Devin names are the tabs of `/analytics/networks` (`webapp/templates/analytics/networks.html:89-97`; route `webapp/routes/analytics.py:887`; `_networks_graphs` `:357`). Builders: `get_network_graph` (`database/analytics.py:1274`), `get_vendor_expenditure_network` (`:7018`), `get_lobbying_influence_graph` (`:5872`), `get_irs527_ecosystem_graph` (`:6442`), `get_state_federal_overlap_graph` (`:7206`). `/analytics/relationships` (`:1189`, `_relationships_graphs` `:430`): `get_donor_cogiving_network` (`:4741`), `get_committee_similarity_network` (`:5116`), `get_candidate_competition_networks` (`:5605`). **Every builder takes a window and limits only; none takes a committee, candidate or race.** Cached per window (`_networks_cache`, `_relationships_cache`, TTL 21600 s, `config.py:96-97`).
- The only entity-scoped network code is the uncached JSON API `/api/analytics/network/focus-sankey` (`webapp/routes/api.py:642`, inline SQL, `focus_node_id`, limits 15–20, max 100) behind the Custom Sankey tab, plus `/api/analytics/network/suggest` (`:498`).
- Candidate detail (`webapp/templates/candidates/detail.html`) and state race detail (`state_race_detail.html`) have tables and stat cards only. They carry 13 `scope_tag(` sites (4 + 9), all registered in `tests/scope_widgets_registry.py` (`:235-258`, `:646-692`); a new windowed tag needs a registry row (+ probe) or `test_every_windowed_tag_site_is_registered` fails.
- Payload contract shared by the existing graphs: `nodes [{id, label, node_type, region, total_amount?, …}]`, `edges [{source, target, edge_type, weight, count?, …}]`, `centrality` (top 100), `summary {node_count, edge_count}` (`database/analytics.py:1331-1352`, `:1503-1520`).
- Viz Lab (`webapp/routes/experimental.py`) is gated off in prod (`config.py:45`); its `network_slice` prototype is a Chart.js bar + tables, not a graph. Not a base for ask 2.

**Ask 3 — why the force graph is unreadable.**
- No graph library. Two hand-written renderers: `webapp/static/js/analytics_networks.js` (`layoutForce :426`, charge 3200–5000 by node count, zoom helper `:377`, generic renderer `:588`, reused by vendor `:1022`, overlap `:1194`, lobbying `:1219`, 527 `:1244`) and `webapp/static/js/relationship_graphs.js` (`layoutForce :367`, pairwise repulsion + spring, 260–280 iterations; `nodeRadius :175` = 5 + √(size+1)/12 clamped 4–18; `bindPanZoom :943`, wheel ×1.1/×0.9 clamped 0.7–3.2; labels only at zoom ≥ 1.4 `:1162`; also `drawArcGraph :1192`, `drawAlluvialGraph :1351`).
- No collision force, no label collision culling, no zoom-to-fit, no focus/dim, no legend-driven filtering. Client caps 90 nodes / 180 edges (relationships `:1704-1730`) and 180 / 320 with per-node caps (networks `:528-547`); server caps via SQL LIMIT + `edge_limit` (`database/analytics.py:1377, 4764, 5149, 5648, 5920, 7068, 7232`; route clamps `webapp/routes/analytics.py:126`, `:1193-1199`).
- d3 is already used from a CDN on `/lobbying/flows` (d3 + d3-sankey) and the Viz Lab state maps; nothing is vendored.
- Playwright is already a project dependency (scraper), so a headless render + overlap measurement is available locally as a verification tool.

## Contract — `database/entity_analytics.py` and `database/entity_network.py` (2026-10-28; steps 3–4 follow it literally)

**Shared conventions.** Pure `database/` modules (no Flask imports); `conn` is the app's psycopg connection used by every builder (`conn.execute(sql, params)` with `?` placeholders, dict-like rows). Window = keyword args `date_from: date | None`, `date_to: date | None`, inclusive, `None` = unbounded (the route converts `TimeScope.start` / `.end`). Receipt base = `isbe_condensed_receipts r` with `r.archived = FALSE AND r.d2_part LIKE '1%' AND r.amount > 0` and `r.received_date` inside the window (the partial index predicate; survey: data-dictionary lines 13–16). Expenditure base = `isbe_condensed_expenditures e` with `e.archived = FALSE AND e.amount > 0`, `e.expended_date` in the window; Part-9 rows are `e.d2_part LIKE '9%'` (lower-case `like` in SQL — `pg_compat` rewrites upper-case LIKE to ILIKE and defeats the partial index, see `docs/outside_spending.md`). Donor identity = `donor_key = LOWER(TRIM(COALESCE(first_name,'') || '|' || COALESCE(last_name,'') || '|' || COALESCE(address1,'') || '|' || COALESCE(address2,'') || '|' || COALESCE(city,'') || '|' || COALESCE(state,'') || '|' || COALESCE(zipcode,'')))` — the `/donors/key/<key>` key (`database/analytics.py:3419-3423`; the `md5(<expr>)` index serves lookups). Donor display name = `TRIM(first_name || ' ' || last_name)` (an organization has no first name). A redacted row (`redaction_requested = TRUE` or `address1 = 'Redaction Requested'`) keeps its name and amounts, has `city`/`state`/`zip5` = None, `redacted = True`, and counts in no geography. Money is `float` rounded to cents; counts `int`; dates `datetime.date`. Every list is capped by an explicit parameter and sorted deterministically (amount desc, then name/id asc).

### `database/entity_analytics.py`

- `ENTITY_KINDS = ("candidate", "race")`; `ENTITY_CACHE_REV = "ea1"` (the routes put it first in their keys).
- `resolve_entity(conn, kind, key, *, election_cycle=None, today=None) -> dict | None`
  - returns `{"kind", "key": str, "label": str, "cycle": int | None, "committee_ids": [int, …] (sorted, unique), "candidate_ids": [int, …], "groups": [{"label": str, "committee_ids": [int, …], "candidate_id": int | None, "family_id": int | None}, …]}`; `None` for an unknown key / kind.
  - `candidate`: `key` = candidate id (str or int); label from `isbe_candidates` (`first_name last_name`); `cycle` None; committees = `isbe_candidate_committees.committee_id` for the candidate **plus every member of an accepted `committee_family`** that contains one of them (`accepted_family_map` in `database/committee_families.py:375`; `status = 'accepted'` only — pending/rejected families add nothing); groups = one per accepted family (label = family label, `family_id`, all its members) then one per remaining committee (label = committee name, `committee_id` alone), labels sorted; `candidate_ids = [id]`.
  - `race`: `key` = the race slug used by `/analytics/state-races/<race_key>` (`_state_race_slug` in `database/analytics.py:2667`); `election_cycle` defaults to the current cycle by `today` (the race pages' rule); rows = `isbe_race_candidacies` rows of that cycle whose slug equals the key; committees = their non-null `committee_id_sbe`; groups = one per candidate (`candidate_id`, label = `candidate_full_name`, that candidate's committees), sorted by label; a committee linked to two candidates of the race sits in both groups and once in `committee_ids`; `label` = the race label the race detail page shows (reuse the builder's formatting); `cycle` = the cycle; no rows → `None`.
- `entity_donor_rows(conn, committee_ids, *, date_from=None, date_to=None) -> list[dict]`: one row per (`donor_key`, `committee_id`) over the receipt base: `{"donor_key", "donor_name", "donor_class": "individual" | "organization", "committee_id": int, "committee_name", "total_amount", "contribution_count", "city", "state" (2-letter upper or None), "zip5" (first five digits or None), "occupation", "employer", "redacted": bool, "first_date", "last_date"}`, sorted by `total_amount` desc, `donor_name`, `committee_id`; `[]` for no committees.
- `get_entity_donors(conn, entity, *, date_from=None, date_to=None, top_n=25) -> dict`:
  `{"groups": [{"label", "committee_ids", "candidate_id", "family_id", "total_amount", "donor_count", "contribution_count", "top1_share", "top5_share", "top10_share", "hhi", "gini", "individual_amount", "organization_amount", "in_kind_total"}], "totals": {the same metrics over the whole entity, donors de-duplicated by key}, "class_breakdown": [{"donor_class", "total_amount", "donor_count"}], "top_donors": [{"donor_key", "donor_name", "donor_class", "total_amount", "contribution_count", "committee_count", "city", "state", "redacted", "groups": [labels]}] (top `top_n` by amount across the entity), "shared_donors": [{"donor_key", "donor_name", "total_amount", "group_count", "groups": [{"label", "amount"}]}] (donors in ≥ 2 groups, amount desc, `top_n`; `[]` when the entity has one group)}`.
  Metric formulas are those of `get_donor_concentration` (`database/analytics.py:1543`): shares = top-k donors' amount / total, HHI = Σ (share × 100)² (0–10,000), Gini over per-donor totals — so a committee's numbers equal the global Donors page's row for the same window. `in_kind_total` = Σ amount of `d2_part = '5A'` rows (archived excluded) per group.
- `get_entity_geography(conn, entity, *, date_from=None, date_to=None, limit_states=20, limit_cities=30) -> dict`:
  `{"states": [{"state", "total_amount", "donor_count", "contribution_count", "share"}], "cities": [{"city", "state", "total_amount", "donor_count", "contribution_count", "share"}], "time_series": [{"month": "YYYY-MM", "total_amount", "contribution_count", "donor_count"}] (every month from the first to the last contribution in the window, zero-filled), "in_state_share": float (IL amount / total), "unknown_amount": float (rows with no state, redacted included), "totals": {"total_amount", "donor_count", "contribution_count"}}`. Shares = amount / entity total. City display as `_city_display` in `database/analytics.py` (reuse).
- `get_entity_risk(conn, entity, *, date_from=None, date_to=None, limit=50, large_threshold=None) -> dict`:
  `{"flags": [{"flag_type", "severity": "high" | "medium", "committee_id", "committee_name", "group_label", "donor_key", "donor_name", "event_date", "month", "value", "baseline", "threshold", "details"}], "threshold": {"large_single": float, "source": "site_wide" | "override"}, "reconciliation": [{"committee_id", "committee_name", "group_label", …the `bulk_d2_receipts_recon` columns (DDL `database/bulk_download_loader.py:1086`)…, "diff"}], "reconciliation_available": bool, "counts": {"large_single_contribution", "monthly_spike", "high_donor_concentration", "reconciliation"}}`.
  - `large_single_contribution`: every receipt-base row of the entity in the window with `amount >= threshold`; threshold = `large_threshold` if given else `max(5000, 2 × p95)` of all site-wide receipt-base amounts, all time (`percentile_cont(0.95)`; the `/analytics/risk` rule, `database/analytics.py:1714`); severity `high` at ≥ 2 × threshold else `medium`; amount desc, `limit`.
  - `monthly_spike`: per committee, monthly sums of the receipt base over the window, zero-filled; flagged when the month ≥ 3 × the trailing 3-month average and exceeds it by ≥ $2,000 (`analytics.py:1955-1994`); with fewer than three prior months use the average of the prior months that exist (≥ 1), the first month is never flagged; `value` = month sum, `baseline` = trailing average, `month` = `YYYY-MM`.
  - `high_donor_concentration`: per group, `hhi >= 4500` with `donor_count >= 3` (from `get_entity_donors`), `value` = hhi, `baseline` = donor_count.
  - `reconciliation`: `bulk_d2_receipts_recon` rows with `committee_id_sbe = ANY(committee_ids)` and `ABS(receipts_minus_d2_total) >= 1000`, all time (the table is all-time), abs diff desc, `limit`; `reconciliation_available = _table_exists(conn, "bulk_d2_receipts_recon")` (`[]` and False when absent).
  Flags are computed from the entity's rows only — never sliced from the global lists.
- `get_entity_relationships(conn, entity, *, date_from=None, date_to=None, limit=25, min_shared_donors=2, donor_pool=2000) -> dict`:
  `{"cogiving": [{"committee_id", "committee_name", "shared_donor_count", "shared_amount_to_entity", "shared_amount_to_committee", "top_shared_donors": [{"donor_key", "donor_name", "amount_to_entity", "amount_to_committee"}] (≤ 5)}], "shared_donors": (as in `get_entity_donors`), "summary": {"entity_donor_count", "donor_pool_size", "cogiving_committee_count"}}`.
  Co-giving = committees **outside** the entity that received receipt-base contributions in the window from ≥ `min_shared_donors` of the entity's top `donor_pool` donors (by amount), ranked by `shared_donor_count` desc then `shared_amount_to_committee` desc, `limit`. Join on the donor-key expression (use `md5(expr) = ANY(?)` so the index serves it).

### `database/entity_network.py`

- `get_entity_network(conn, entity, *, date_from=None, date_to=None, caps=None) -> dict` with `caps` defaulting to `{"donors": 40, "vendors": 25, "transfers": 15, "ie_spenders": 15}` (top-N per class by weight; the dropped count per class is reported).
  `{"entity": entity, "nodes": [{"id", "label", "node_type": "donor" | "committee" | "candidate" | "vendor", "role": "entity" | "candidate" | "donor" | "vendor" | "transfer_source" | "ie_spender", "group_label", "total_amount", "redacted"?}], "edges": [{"source", "target", "edge_type", "weight" (abs USD), "count", "edge_label", "edge_description", "weight_unit": "usd", "metric_label", "source_table", …per-type fields}], "centrality": [{"node_id", "label", "node_type", "weighted_degree", "degree"}] (as `_compute_graph_centrality`, `database/analytics.py:4437`; ≤ 100), "summary": {"node_count", "edge_count", "edges_by_type": {edge_type: n}, "truncated": {class: dropped}, "edge_type_definitions": {edge_type: {edge_label, edge_description, weight_unit, metric_label}}, "window": {"date_from", "date_to"}}}`.
  - Node ids: `committee:<id>`, `candidate:<id>`, `donor:<donor_key>`, `vendor:<sha1-16 of the normalized payee name>`, `transfer:<sha1-16 of the normalized payer name>` — except that a 2A payer whose normalized name equals exactly one `isbe_committees.name` (normalized `LOWER(TRIM())`, exact only) becomes `committee:<id>`.
  - Edge types: `donor_committee` (1A receipts, donor → entity committee), `in_kind_donor_committee` (5A), `transfer_in` (2A, payer → entity committee), `committee_vendor` (expenditure base minus Part 9, entity committee → vendor; payee = the expenditure's name fields, business name in `last_name`), `independent_expenditure` (Part-9 rows attributed to the entity's candidates with the matcher in `database/outside_spending.py` — `attribute_part9_rows` / the candidate-name key — spender committee → candidate; fields `support_oppose: "S" | "O"`, `signed_weight` = +amount for S, −amount for O, `weight` = amount), `committee_candidate` (entity committee → its candidate, weight = the committee's receipt-base total in the window). A Part-9 row naming a candidate outside the entity, an archived row of any kind, and a zero/negative amount produce no edge.
  - Edge semantics live in a module-level dict in `entity_network.py` (not in `_EDGE_TYPE_SEMANTICS`); the renderer reads `edge_label` / `edge_description` / `metric_label` / `weight_unit` from the edge and `summary.edge_type_definitions`.
  - Projections for the Network tab views (step 8) are pure functions of this payload: `money_flow(payload)` (sankey: donor classes + transfer sources + IE spenders → committees → vendor classes), `vendor_network(payload)` (committees ↔ vendors, IE spenders included), `ego_force(payload)` (the graph as is). Their shapes are fixed in step 8.
