# Item 4 — Server-side scheduled data refresh (nightly run, 5 am check, data status)

**Owner:** Fable · **Builder:** opus-builder-ops · **Branch:** `scheduled-refresh` · **Scope class:** Cross-Component (schema + database module + scripts + systemd units + one web page + docs; no prod install by the builder) · **Budget:** 150 min (M1 45 · M2 40 · M3 35 · M4 30) · **Ordered by Devin 2026-10-29 ≈06:55Z** (to-do item 4).

## Devin's ask (to_do/to_do_10_28_26 item 4, paraphrased)

A server-side update that runs on its own every morning around 3 am CST and refreshes FEC, ISBE and every other source we load; at 5 am a check that the run happened and what changed across the data; a list of loads that are not automated (IRS 527 and the like) with whether their download can be automated and, if not, a cadence where Devin downloads by hand into a local folder that we push to prod; a data status that includes the manual items so we know how old each dataset is.

## Interpretation and decisions (journaled; Devin ratifies at review)

- **D1 Nightly = the existing canonical chain, daily.** `scripts/refresh_prod_chain.sh` (ISBE download → row-count gate → `sunshine-import` → `sync-fec-il-federal --refresh-cache` → `run-cross-matching --only all` → `refresh-analytics --with-snapshot` (+ entity rebuild, warm) → restart) is already the refresh; the new `scripts/nightly_refresh.sh` wraps it with a `flock` on `shared/refresh.lock`, a run record and a log at `shared/logs/nightly-<stamp>.log`. Verify the chain passes `--refresh-cache` to the FEC sync (the silent no-op trap; fix the chain if it does not). Add one new chain step, non-fatal, gated on `SOCRATA_APP_TOKEN` in the env: `import-chicago-phase1 --app-token "$SOCRATA_APP_TOKEN" --upsert` (an API pull, so automatable). The hourly Schedule E timer and the Sunday FEC timer stay; `nightly_refresh.sh` takes the same lock file the Sunday script uses if it has one (read `scripts/sync-fec.sh`), else documents the overlap rule.
- **D2 Run record in the DB**, table `data_refresh_runs` (`id`, `kind` nightly|manual, `started_at`, `finished_at`, `status` running|ok|failed, `exit_code`, `log_path`, `snapshot_before` JSONB, `snapshot_after` JSONB, `diff` JSONB, `check_status`, `checked_at`, `notes`), created in `database/schema.sql` with `CREATE TABLE IF NOT EXISTS` so `init-db` applies it. Snapshots = per source table: row count, `MAX(<natural date column>)`, taken by `database/data_refresh.py::snapshot_counts(conn)`. Diff = rows added, new max date, per table.
- **D3 Manual datasets** are first-class in the status: `database/data_refresh.py::DATASETS` — label, key, automated (bool), table, natural date column, cadence text, loader command, placement folder. Rows: ISBE (auto, nightly), FEC Schedule A (auto, Sunday sync + nightly), FEC Schedule B (auto, monthly backfill — mark "semi": the backfill is a command Devin runs; say so), FEC Schedule E (auto, hourly), Chicago Phase 1 (auto, nightly, needs token), IL SOS lobbying (manual, weekly, `import-lobbying --file …`), IRS 527 (manual, monthly, `import-irs527 --file … --illinois-only`; the automation probe belongs to to-do item 5 in the other session — link to `docs/runbooks/irs527_data.md`, do not redo it), OpenBook (manual, as needed, `import-openbook-batch`). Table names and date columns come from `.claude/data-dictionary.md`; verify each against `database/schema.sql` before use. `data_manual_loads` table (`dataset_key`, `source_file`, `file_date`, `loaded_at`, `rows_loaded`, `notes`) written by `scripts/manual_load.sh <dataset> <file>` which runs the dataset's loader command then records the load via `scripts/data_refresh_cli.py record-manual`. `cli/commands.py` is off-limits (another session's dirty file), hence the separate entry script.
- **D4 The 5 am check** is `scripts/nightly_check.py`: finds today's nightly run (local date America/Chicago), computes/stores the diff, writes `shared/refresh_runs/<YYYY-MM-DD>.md` (status, per-step durations from the chain's `STEP_N_START/END` markers in the log, the diff table, freshness per `database/data_freshness.py`), sets `check_status` ok|missing|failed, exits non-zero on missing/failed so systemd shows the unit failed. No email/Slack (nothing configured); the result is on the site (D5) and in `systemctl --failed`.
- **D5 Page `/data-status`** (new blueprint `webapp/routes/data_status.py`, template `webapp/templates/data_status.html`, registered in `webapp/app.py`): the datasets table (dataset, automated?, cadence, last data date, last load, age days, stale flag by the `data_freshness` thresholds where they exist) and the last 14 runs (started, duration, status, check status, diff summary). One link "Data status" added to the freshness strip in `base.html` (nothing else in the strip changes). Public, no inputs, read-only, short `RouteCache` not needed (two small queries); `Cache-Control` like other anonymous pages.
- **D6 systemd units** in a new `deploy/systemd/`: `ilcf-nightly-refresh.service` (+ `.timer`, `OnCalendar=*-*-* 03:00:00 America/Chicago`, `Persistent=true`, `RandomizedDelaySec=300`) running `/bin/bash /srv/illinois_campaign_finance/app/scripts/nightly_refresh.sh`; `ilcf-nightly-check.service` (+ `.timer`, `05:00 America/Chicago`) running the venv python on `scripts/nightly_check.py`. Env from `/srv/illinois_campaign_finance/shared/.env` via `EnvironmentFile=`. Install is Devin's (runbook).
